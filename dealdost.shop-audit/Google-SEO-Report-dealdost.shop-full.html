This report presents a comprehensive SEO audit of dealdost.shop for a E-commerce / Affiliate deals aggregator (Amazon & Flipkart deals sourced from Telegram) site, generated on August 03, 2026. Findings combine technical, content, schema, performance, visual, and search-readiness evidence as available.

2. Audit Categories

2.1 Technical SEO

Score: 22/100

What Works

  • HTTPS enforced correctly with a valid 301 redirect from http:// to https://
  • TLS certificate covers both apex and www hosts
  • Mobile viewport meta tag present and correct on all routes
  • Content is eventually renderable by a JS-executing crawler (Playwright did extract real product text after a long render) — not a hard JS-blocking wall, purely a performance/timeout risk

Findings

Production is running the Vite dev server, not a production build Critical

https://dealdost.shop/ returns raw dev-server HTML: `/@react-refresh` HMR bootstrap, `<script type="module" src="/@vite/client">`, and unbundled `/src/main.tsx` returns HTTP 200 directly. No hashed `/assets/*.js` production bundle exists anywhere. Cache-Control: no-cache is set site-wide.

Recommendation: Run `pnpm --filter @deals/web build` to produce apps/web/dist/, and serve that static output via nginx instead of the vite/pnpm dev process.

No robots.txt or sitemap.xml reach crawlers Critical

Both /robots.txt and /sitemap.xml return HTTP 200 but the body is the SPA's index.html shell. sitemap_discovery.py found declared:[] found:[] — nothing valid exists. Files already exist in apps/web/public/ but the deployed dev server doesn't serve static assets at all.

Recommendation: Fix nginx/static routing so real files in apps/web/public/ (or dist/) are served before the SPA catch-all; redeploy the production build.

No canonical tag, meta description, or per-route title anywhere in raw HTML Critical

Every one of 9 routes tested returns byte-identical <head> content (same Content-Length: 709, same ETag). Seo.tsx (react-helmet-async) is coded to set these client-side, but given the ~17s render time, crawlers may never execute the JS that sets them, and Google deprioritizes JS-injected rel=canonical.

Recommendation: Resolves automatically once the production build is deployed (index.html already has static description/canonical in the repo). Verify each route gets a distinct Seo.tsx title/canonical post-fix.

No indexable per-deal/product URLs Critical

Routes are limited to /, /category/:name, /digest, /search, /trending, /price-drops, /assistant, /login, /signup. No /deal/:id or /product/:id route exists — individual deals only render as cards inside listing pages.

Recommendation: Add a /deal/:id detail route with server-renderable-equivalent meta tags per deal; include in the sitemap. Backend data (GET /v1/deals/:id, GET /v1/products/:id) already supports this.

www.dealdost.shop serves duplicate content with no redirect and no canonical High

https://www.dealdost.shop/ returns 200 OK with byte-identical body/ETag to the apex domain. TLS cert covers both hosts so there's no blocker to fixing this at the nginx/DNS level.

Recommendation: Add an nginx server block that 301-redirects www.dealdost.shop to https://dealdost.shop for all paths.

Missing all standard security headers High

Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, and Permissions-Policy are all absent from every response.

Recommendation: Add via nginx add_header: HSTS, X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, Referrer-Policy: strict-origin-when-cross-origin, and a CSP scoped to real script/style/API origins once dev-mode injections are removed.

No structured data (Schema.org) anywhere on the live site High

Playwright-rendered structured-data extraction returned block_count: 0 on every route checked, despite visible product cards in rendered text.

Recommendation: See Schema category — Organization/WebSite JSON-LD is already coded and should appear automatically once the production build ships; add BreadcrumbList and ItemList as new work.

Referenced favicon/manifest assets soft-404 to the SPA shell Medium

/icon-192.png and /manifest.json both return HTTP 200 with Content-Type: text/html (the SPA shell) instead of image/png or application/json. The deployed index.html references stale asset paths that predate the current repo's favicon.svg/apple-touch-icon.png.

Recommendation: Resolves automatically once the current build is deployed. Separately, configure nginx to return a real 404 for unmatched static-looking paths (*.png, *.json, *.ico).

Soft-404s: unknown paths return 200 with the homepage shell Medium

GET /nonexistent-page-xyz returns 200 OK, byte-identical to /, with no noindex signal in the raw HTTP response.

Recommendation: Ensure the client router's not-found state sets noindex via Seo.tsx, and verify it fires given current rendering performance.

2.2 Content Quality

Score: 15/100

What Works

  • Above-the-fold copy (once rendered) is clear and value-prop focused
  • Real, differentiated product data (price, discount %, price-drop %, ratings, coupon text, bank offers) already exists in the backend and is richer than most competitors expose

Findings

No individual deal/product pages exist Critical

Deals only appear as DealCard components inside listing pages. DealCard fires the buy action via onClick, not an <a href>, so there isn't even an anchor to expose. This is the root cause of nearly every other content finding.

Recommendation: Introduce a permalink per deal (/deal/:slug-or-id) with title, price, image, source badge, and stable canonical URL.

SEO metadata is coded but never reaches the live page Critical

Seo.tsx (react-helmet-async) is wired into Home.tsx and Category.tsx to inject per-route title/description/canonical/OG/JSON-LD, but full-render checks on three routes all returned the identical static head. Directly caused by the dev-server-in-production issue.

Recommendation: Fix production deployment (see Technical); re-verify Helmet output renders per-route afterward.

No FTC/ASCI affiliate disclosure anywhere on the site Critical

Zero matches for 'disclosure', 'affiliate', 'About', 'Contact', 'Privacy', 'Terms', 'FTC', or 'commission' anywhere in rendered HTML/body text. No footer exists. No /about, /disclosure, /privacy, /terms, or /contact route exists in App.tsx at all.

Recommendation: Add a footer present on every page with an affiliate disclosure statement, About blurb, Privacy Policy, Terms, and a real contact method. Compliance issue, not just SEO.

Category pages carry no unique content beyond a templated one-line heading High

Rendered text for /category/electronics after full JS render was just nav chrome plus a single un-capitalized heading ("electronics Deals") with no supporting copy.

Recommendation: Add a short (100-200 word) category intro — what appears here, update cadence, curation criteria — written once per category, not templated.

Deal 'content' is verbatim marketplace copy with no original commentary High

product_title is copied directly from the first line of the raw Telegram message (itself the marketplace's own listing title) with no rewriting or added commentary. No Experience or Expertise signal per Google's Sept 2025 QRG.

Recommendation: Add one original sentence per deal at ingestion/curation time using existing previous_price/price_drop_percent data rather than relying solely on the scraped title.

No Product/Offer/ItemList schema exists even in source code High

Home.tsx's JSON-LD only covers Organization and WebSite. No per-deal schema exists, and there's no permalink URL to anchor it to yet.

Recommendation: Add Product+Offer JSON-LD once per-deal pages exist; add ItemList to listing pages in the meantime.

Inconsistent client-side hydration blocks crawler visibility on some routes Medium

/trending fully rendered its product grid within the Playwright render budget; /category/electronics did not, showing only nav + heading after ~16s.

Recommendation: Investigate route-to-route fetch/render timing differences; prioritize SSR or static pre-rendering for listing pages.

Duplicate content risk from unmodified marketplace titles Medium

Because product_title is copied verbatim from source listings, the same title strings very likely appear across many other deal-aggregator sites/Telegram channels republishing the same feeds.

Recommendation: Covered by the original-commentary fix plus stable per-deal URLs — treat as one connected fix.

2.3 On-Page SEO

Score: 15/100

What Works

  • Category page title/description template (Seo.tsx) is reasonable, just not yet differentiated with real content

Findings

All 9 routes tested return the exact same 709-byte head with no per-route title variation, poor for CTR and self-competing pages in SERPs.

Recommendation: Ship the production build so Seo.tsx's per-route titles/descriptions render; add a static fallback description/canonical in index.html itself as already exists in the repo source.

SXO audit found 0 <h1>, 0 <h2> on rendered / and /price-drops after full JS execution.

No internal linking to individual deals High

DealCard uses onClick handlers instead of <a href> links, so there is no crawlable internal link graph pointing at individual products.

Recommendation: Once per-deal permalinks exist, link DealCard titles to them with real <Link>/<a> elements in addition to the buy button.

2.5 Performance (Core Web Vitals)

Score: 54/100

What Works

  • CLS = 0 on both routes tested — no layout-shift issues
  • TBT (INP lab proxy) is 120-130ms, well under the 200ms 'good' threshold — main-thread JS execution itself is not heavy

Findings

LCP is 16.1s (home) / 17.2s (trending) — ~6.5x over the 'poor' threshold Critical

Lighthouse mobile lab run: LCP 16,128ms / 17,168ms against a 2,500ms 'good' threshold. 90% of the LCP time on /trending is 'Load Delay' — the browser resolving unbundled dev-mode JS module chains before it even starts fetching the LCP image. FCP (9.0-9.3s), Speed Index (12.8-12.9s), and TTI (18.7-19.4s) are all similarly poor. Lighthouse Performance score: 54/100 on both routes.

Recommendation: Deploy the production `vite build` output instead of the dev server. Expected to cut LCP from ~16-17s to low single digits on its own.

Static JS assets served without compression High

The largest JS chunk (928KB, unminified) returns HTTP 200 with no Content-Encoding header despite the client advertising gzip/br support. Lighthouse estimates 1.7MB of savings from text compression alone sitewide.

Recommendation: Enable gzip/brotli in nginx for application/javascript, text/javascript, and text/css once the production build is deployed.

LCP element uses loading="lazy" despite being above-the-fold High

The first product card image (Lighthouse's identified LCP element on /trending) has loading="lazy", delaying its fetch until layout completes.

Recommendation: Use loading="eager" plus fetchpriority="high" for the first N above-the-fold cards; keep lazy-loading for the rest of the grid.

TTFB is borderline (230ms / 744ms observed) Medium

Root document TTFB is right at or above the 200ms 'good' threshold on both routes; likely reflects backend/cold-start latency rather than static-asset serving.

Recommendation: Re-check after the production build ships; consider short-TTL response caching on feed endpoints given the 10-minute poller cadence.

What Works

  • Alt text exists via the product title, even if not always clean/descriptive

See Performance category — the first above-the-fold product image uses loading="lazy", directly harming LCP.

Recommendation: Switch to eager/fetchpriority=high for the first visible card image.

Alt text is raw scraped marketplace title, not always clean Low

Titles sometimes include marketplace boilerplate ("Buy X Online at Best Price...") rather than clean descriptive text.

Recommendation: Reuse existing title-cleaning logic (used for search indexing) for displayed/alt text as well.

2.7 AI Search Readiness (GEO)

Score: 10/100

What Works

  • Once fully rendered, Playwright does successfully extract real product text, meaning Google's JS-executing systems are not entirely blind to content — the ceiling is render-time, not a hard block

Findings

AI crawlers that don't execute JavaScript see nothing Critical

GPTBot, ClaudeBot, and PerplexityBot user agents were tested directly against the raw response — all received an identical 709-byte empty shell (<div id="root"></div> only), regardless of User-Agent.

Recommendation: Fix the production deployment first, then evaluate SSR/prerendering (e.g., prerender-on-bot-UA middleware) so first-response HTML contains real deal content.

No real robots.txt or llms.txt — well-known AI-crawler paths fall through to the SPA shell Critical

/robots.txt, /llms.txt, /sitemap.xml, and /ai.txt all return HTTP 200 byte-identical to the homepage shell.

Recommendation: Fix static-file serving precedence; add explicit Allow rules for GPTBot/OAI-SearchBot/ClaudeBot/PerplexityBot plus a Sitemap: directive, and an llms.txt summarizing the site's purpose and key routes.

No permalink URL per deal blocks AI citation structurally Critical

Even after fixing rendering, an AI answer engine has no stable URL to cite for a specific deal — only an aggregate listing page whose contents rotate every ~10 minutes.

Recommendation: Add /deal/:id permalink pages with server-rendered title, description, OG tags, and Product/Offer JSON-LD.

No meta description, Open Graph, or Twitter Card tags anywhere High

The entire <head> (raw or rendered) contains only charset, viewport, theme-color, and <title>. This also produces broken link previews when DealDost URLs are shared on Telegram/Twitter/WhatsApp — ironic given Telegram is the product's own distribution channel.

Recommendation: Add static or dynamically-injected meta description + OG/Twitter tags per route.
